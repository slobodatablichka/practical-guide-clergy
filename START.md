# START — Практическое руководство для священнослужителя

## 1. Назначение проекта

Проект — самостоятельная **справочно-учебная система**, созданная в рамках изучения курса БПДС **«Практическое руководство для священнослужителя»**.

Проект не заявляется как официальный ресурс БПДС. Его назначение — подготовка к зачёту, систематизация экзаменационных тем, сопоставление учебных и справочных источников и удобная работа с первоисточниками.

**Важно:** не смешивать этот проект с:
- тестом по апологетике (`apologetika-test`);
- другими семинарскими сайтами и учебными материалами.

Главный объект системы — **экзаменационный вопрос / нормализованная тема**. Учебники и другие книги выступают независимыми источниками материала по теме.

Каноническая модель проекта:

`билет → экзаменационный вопрос → нормализованная тема → источники → ответ / фрагмент первоисточника`

Количество источников не является архитектурным ограничением проекта.

## 3. Каноническая структура экзаменационного материала

В системе:

- **30 билетов**;
- по **6 вопросов** в каждом билете;
- всего **180 экзаменационных позиций**;
- после нормализации повторяющихся формулировок — **171 каноническая тема**.

Принцип:

- исходная формулировка вопроса билета сохраняется;
- нормализованная тема используется как общий смысловой идентификатор;
- одна тема может встречаться в нескольких билетах;
- ответы учебников привязываются к нормализованной теме, но в билете пользователь видит исходную экзаменационную формулировку.

Основные данные:

- `source/tickets-original.txt` — исходные билеты;
- `data/ticket-questions.json` — 180 позиций;
- `data/topics.json` — 171 тема;
- `data/textbooks.json` — реестр учебников.

## 5. Система полноты материала

Внутри данных сохраняется техническая шкала:

- `rel_5`
- `rel_4`
- `rel_3`
- `rel_2`
- `rel_1`

Она означает, насколько материал конкретного учебника покрывает конкретный экзаменационный вопрос.

В пользовательском интерфейсе `rel_N` **не показывается**.

Вместо него используется пятикубиковая шкала полноты:

- `■■■■■` — полный ответ;
- `■■■■□` — почти полный;
- `■■■□□` — частичный;
- `■■□□□` — отдельные сведения;
- `■□□□□` — прямого ответа нет.

Полные данные учебника и словесная расшифровка доступны во всплывающей подсказке.

Важно различать:

- **полнота материала учебника** — внутренняя характеристика источника;
- **оценка ответа пользователем 1–5** — обратная связь о качестве и полезности показанного ответа.

Эти две шкалы не смешивать.

Первичная разметка `rel` построена автоматически и является рабочей, а не окончательной содержательной аттестацией.

Правило формирования слабых ответов:

- при `rel_2` / `■■□□□` показываются только полезные сведения по существу вопроса; метатекст вроде «в учебнике…», «учебник не даёт полного ответа…» убирается;
- при `rel_1` / `■□□□□` содержательный ответ не достраивается; допустима короткая констатация: **«Прямого ответа в этом источнике нет.»**

## 6. Интерфейс ответов

В билете у каждого вопроса пользователь выбирает источник:

- **Нефёдов**
- **Сильченков**

Рядом показывается шкала полноты.

Правила интерфейса:

1. одновременно открыт только **один ответ**;
2. повторное нажатие на уже выбранный источник закрывает ответ;
3. выбор другого учебника заменяет открытый ответ;
4. открытие ответа другого вопроса закрывает предыдущий;
5. технические строки вида `Уч.1`, `Уч.2`, `rel_5`, `Источник: #003` пользователю не показывать;
6. переход к первоисточнику оформлен одной ссылкой **«Подробнее в учебнике»**;
7. форма обратной связи называется **«Оценить ответ»**.

Навигация сайта:

- **Билеты**
- **По учебнику**
- **Поиск**

## 7. Ридер учебников

`reader.html` работает в двух разных режимах.

### 7.1. «Подробнее в учебнике»

Используется из ответа на экзаменационный вопрос.

Поведение:

- открывает точное место в выбранном учебнике;
- подсвечивает использованный фрагмент;
- позволяет вернуться к тому же вопросу;
- **не изменяет** сохранённое место обычного чтения.

### 7.2. «Читать учебник»

Доступно в шапке сайта рядом с **«Скачать учебник»**.

Поведение:

- открывает учебник без подсветки;
- при первом входе — с начала;
- затем — с последнего места чтения;
- позиция сохраняется в `localStorage`;
- место чтения хранится отдельно для каждого учебника.

### 7.3. Интерфейс ридера

В верхней части:

- фамилия автора и краткое название книги;
- текущий раздел одновременно является раскрывающимся оглавлением;
- стрелки `‹` и `›` переключают соседние разделы;
- отдельная нижняя строка оглавления отсутствует.

Пример:

`Нефёдов — Таинства и обряды`

`‹  Виды Требников и их содержание ▾  ›`

Повторяющиеся названия в оглавлении сокращаются, но контекст сохраняется там, где без него подраздел становится непонятным.

## 8. Supabase и система отзывов

Supabase-проект:

`practical-guide-clergy`

Регион:

`eu-north-1`

Основная таблица:

`public.answer_feedback`

Отзыв относится к паре:

`topic_id + book_id`

То есть один и тот же вопрос по Нефёдову и по Сильченкову оценивается независимо.

### Пользовательский отзыв

При первом использовании:

- имя или псевдоним — обязательно;
- оценка ответа — 1–5;
- комментарий — необязательно.

Имя хранится локально в браузере.

Одна актуальная запись существует для:

`user_id + topic_id + book_id`

Повторная оценка обновляет запись, а не создаёт новую.

Сохраняются:

- `user_id`;
- `display_name`;
- `topic_id`;
- `book_id`;
- `question`;
- `source_rel`;
- `rating`;
- `comment`;
- `answer_revision`;
- `view`;
- `ticket`;
- `position`;
- `created_at`;
- `updated_at`.

### Безопасность

- anonymous sign-ins включены;
- RLS включён;
- посетитель читает и изменяет только собственные отзывы;
- публичный сайт не получает административных ключей;
- используется только publishable key;
- допустимы только 171 каноническая тема;

## 10. Канонические правила работы

1. **Не смешивать этот проект с апологетикой или другими учебными сайтами.**
2. Перед изменениями восстанавливать состояние проекта **из репозитория**, а не только из памяти чатов.
3. Перед началом работы проверять:
   - правильный репозиторий;
   - ветку `main`;
   - актуальность `origin/main`;
   - текущий HEAD;
   - чистоту рабочего дерева.
4. Исходные формулировки билетов сохранять без самовольной редакции.
5. Нормализованные темы не подменяют исходные вопросы.
6. Учебники обрабатываются как **независимые источники**.
7. Не достраивать отсутствующий материал общими знаниями.
8. Если прямого ответа в учебнике нет, это фиксируется явно.
9. Первичные автоматические сопоставления и `rel` подлежат ручной содержательной проверке.
10. Во внешнем интерфейсе использовать человеческую шкалу полноты, а `rel_N` оставлять техническим внутренним полем.
11. Пользовательскую оценку 1–5 не смешивать с полнотой материала.
12. «Подробнее в учебнике» и «Читать учебник» — два разных сценария:
    - источник ответа с подсветкой;
    - обычное чтение с сохранением позиции.
13. Не публиковать приватные CSV/HTML с именами и комментариями пользователей.
14. При изменении структуры данных сохранять совместимость:
    `ticket → topic → book → answer/source`.
15. При добавлении новых учебников не превращать интерфейс в длинный список технических источников: экзаменационный вопрос остаётся главным объектом системы.
16. Новые книги подключать только через единый конвейер: **файл книги → индекс → оглавление → полнотекстовый корпус → сопоставление с 171 темой → первичная полнота → ручная проверка → пользовательское представление**.
17. Не требовать от каждого источника покрытия всех 171 тем; источник показывается там, где он реально полезен.
18. При росте библиотеки основной интерфейс должен различать основные ответы и дополнительные источники, а не выводить все книги равнозначным длинным рядом.
19. Развивать 171 нормализованную тему из технической сущности в пользовательский учебный объект: тема может объединять билеты, краткий ответ, источники и связанные темы.
20. Поиск развивать в двух направлениях: **по экзаменационным вопросам/темам** и **по полным текстам источников**.
21. Стратегическая концепция проекта хранится в `docs/PROJECT-CONCEPT.md`.
22. Изменения сначала обсуждаются концептуально; после утверждения реализуются и фиксируются в документации проекта.

## 12. Следующий рабочий контекст

Ближайшие обсуждаемые направления:

1. **Качественное улучшение поиска**:
   - один результат = один экзаменационный вопрос;
   - более качественное ранжирование;
   - формы слов, опечатки, контролируемые синонимы;
   - короткий фрагмент, объясняющий совпадение;
   - в перспективе разделение:
     - поиск по экзаменационным вопросам;
     - поиск по полным текстам учебников.

2. **Масштабирование библиотеки до шести и более источников**:
   - подготовить архитектуру библиотеки;
   - затем подключать новые книги по единому конвейеру;
   - не назначать книге роль и охват до анализа её содержания.

3. **Развитие пользовательской темы** как объединяющего учебного объекта: билеты → тема → ответы → первоисточники → связанные темы.

Принятая стратегическая модель подробно закреплена в `docs/PROJECT-CONCEPT.md`.
